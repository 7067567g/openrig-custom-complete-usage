# 案例 04 — 跨三仓的文档治理

## 问题

同一个产品有三套文档面——控制面、源码仓、清洗后的使用仓——怎么让智能体不去读错那一套，又怎么让地图本身不腐烂？

## 背景

三套面回答不同问题，但共用一套词汇：

- **控制面**：目标、决策、验收、run 证据；
- **源码仓**：代码结构、随包参考文档、发布说明；
- **使用仓**：清洗后的示例、运维指南、过程档案。

智能体经常落到错误的面：包内 `README` 当成项目入口、历史 run 当成现行规范、示例仓当成源码事实。

## 做法

三轮，每轮都以独立评审收尾：

1. **盘点（只读）**：对每个候选入口记录路径、规模、哈希、git 状态与判定（`canonical / stale / duplicate / wrong-location`）；把可能被改的文件先复制一份"改前内容"，让后续 diff 能证明"只加了一行指针"。
2. **建图**：控制面一张跨仓总图，两个仓各一张本地图。每张图写清三件事：哪个面回答什么、"我要做 X → 读哪里"、"正确位置 vs 常见错位"。
3. **校正入口**：每个入口文档只加一行最小指针，至少三处已知错位显式改道，并跑各仓原生文档检查。

验收是机械的，不是叙述的：

```text
14/14 入口同时带"本地图"与"跨仓总图"指针
三图互链可达；相对链接解析：0 断链
指针/改道 diff 纯追加：删除行 0
各仓原生文档检查：与预先记录的基线同集合
```

## 结果

- 三张地图、16 类任务路由、10 类常见错位。
- 14/14 入口同时指向本地图与跨仓总图。
- 3 处显式改道（包内 README、历史 runs、usage 当源码）。
- 链接检查：新增链接全部可解析，0 断链。

## 收口之后才发现的问题（最有价值的部分）

两个缺陷是在工作流关闭并验收之后才发现的：

1. **已发布地图里的陈旧口径**：有一行仍在描述更早、更小的改动范围。地图正是下一个智能体要读的东西，所以地图里的陈旧行比报告里的更糟。
2. **裸数字**："差异是 3 行"在写下时是真的，随后变成 4 行、5 行。没有人能判断它何时失真。

两者都用小的专门工作流修掉（见案例 05），而不是重开主工作流。

## 可复用规则

- **数字必须带命令与时点**：正文里的数字要么旁边就有复现它的命令与取数时刻，要么改成定性表述；如果一个数字改变不了读者的判断，就该删掉。
- **缺失性断言必须负向核验**："这个文件不存在"只能用指向**该对象本身**的命令证明，不能用长得像的路径。
- **验证必须写在最后一次产品写入之后**：在最终编辑之前写下的记录，描述的是一个已经不存在的状态。
- **需要免责声明的指针不算修好**：把内容移出脆弱的容器，而不是给它加注解。
- **把判断机械化**："没有单元格含奇数个反引号"比肉眼看渲染结果更能抓住被竖线切断的表格。

## 它证明了什么

文档治理本质上是**证据纪律**：地图是容易的部分，成本全部花在"证明每一条主张在读者读它的那一刻仍然成立"上。
