# 案例 05 — 返工环与微工作流

## 问题

一个工作流已经关闭并验收。之后有人发现缺陷只涉及一个文件、一句话。是重开整个工作流，还是做更小的事？而返工本身又揭示了评审的什么？

## 背景

同一张地图上的两个收口后缺陷：

- 一行仍在描述已被取代的改动范围；
- 一句"差异是 N 行"随着文档增长不断漂移。

两个都是真实的产品缺陷：地图正是下一个智能体要读的东西。

## 做法

两个专门的微工作流，各自一个执行步、一个评审步：

```text
patch_x09（改）→ qa_x09（只读验证）      → 一轮通过
patch_x01（改）→ qa_x01（只读验证）      → FAIL → patch_x01 返工 → PASS
```

每个微工作流：

- 只被授权改**一到两个文件**，按路径列明；
- 不得新建 run 目录（那会改变 canonical 计数，并让一个无关检查失效）；
- 产出修补记录：改前/改后文本、命令、退出码、文件清单；
- 以独立只读评审收尾。

## 结果

**x09（一轮）**：该行改写为当前口径，措辞从"缺失断言"改为"归属陈述"。评审一次通过。

**x01（一次失败、一次返工）**：数字对，形式不对：

```text
初版   ："R1 实测 3 行；加改道行后为 5 行"
评审   ：FAIL —— 裸数字、无时点、无"以命令为准"
返工   ：X01 改为归因（不写数字，指向 §7 命令）
         §7 注释改为两行：
           # 差异行数（2026-11-15T12:34:44Z 实测 5 行）
           # 该数随文件变动而变，以本行命令的当前输出为准
评审   ：PASS
```

## 它证明了什么

- **微工作流适合收口**：一个文件、一条断言、一条命令、一个评审者。证据链不断，也不用重开已关闭的 run。
- **评审失败必须回到原执行者**：返工发生在原步骤、原授权内，没有"由评审者代为修复"。
- **数字属于命令旁边**：返工没有改值，只是改了"值被允许待在哪里"。
- **修补不要新建 run 目录**：一个新目录会悄悄改掉别的文档断言的计数。

## 可复用规则

1. 一个微工作流 = 一个边界清晰的小改动 + 一次独立只读评审。
2. 评审清单写成**可执行的修正项**，不是意见；执行者逐条落实。
3. 数字必须出现时，写成 `时点 + 值 + "以命令输出为准"`；否则用定性表述并指向命令。
4. 每份修补记录同时列出**改了什么**与**没改什么**；后者在后续授权变化后仍须保持为真。
