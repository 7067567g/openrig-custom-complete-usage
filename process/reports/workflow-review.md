# Gemini 4 Argon 对长任务工作流的「档次评价」

- 原文如下（未编辑）
- 结论：**A 档（约 85/100）**；单机/自用场景很强，做多租户 SaaS 则不在这个档位

---

既然当朋友聊，那我就不整那些虚头巴脑的客套话了，直接给你拍个砖。

先给结论和打分：如果按 S/A/B/C 分档，在“单机开发者工具/研发自动化”这个赛道里，我给它打 **A 档（百分制的话 85 分左右）**。

如果拿去做商业化 SaaS 卖给大企业，它可能连 B 都算不上（因为没多租户、没强安全隔离、没分布式）；但如果是**给你们团队自己用，用来啃硬骨头、跑真实生产环境的研发长任务**，这套东西绝对能打，而且比市面上 90% 照着 LangChain 教程搭出来的“花架子”要强得多。

下面挨个回答你的四个问题。

---

### 1. 它大概是什么水平、算不算“有想法的工程”？

**绝对算有想法的工程，而且是那种“真正被 LLM 坑惨过、交足了学费”之后才能憋出来的实战派工程。**

市面上很多做 Agent 的人，还在迷信什么“无限上下文”、“多 Agent 群聊”、“自主演进”，本质上是在用确定性的代码去放纵一个概率性模型的发散。结果就是跑一个小时，前 15 分钟在干活，后 45 分钟在自己的幻觉里打转，Token 烧光，代码改烂。

你们这套架构，最牛的地方在于**极其清醒的克制**。你们认清了现阶段 LLM 的本质——它就是一个容易疲劳、容易失忆、还会撒谎的临时工。所以你们不用什么复杂的图框架（LangGraph），也不用死重的分布式引擎（Temporal），而是退回到最古老但最可靠的 **UNIX 哲学 + 契约式编程**。

用文件系统做状态机，用进程生灭做垃圾回收（GC），用 Git 做事务回滚。这不叫“平庸的重复造轮子”，这叫**架构祛魅**。很多团队兜了一大圈，最后发现最稳的也是这套东西。

---

### 2. 最值钱的那个设计是什么？

如果在你们这一堆特性里只挑一颗明珠，最值钱的绝对是：**“每一轮起新进程，上下文一个字不继承，只传落盘的契约文件”**（再配合独立的验证轮）。

这就是所谓的 **“上下文断舍离”**。
做过长周期 Agent 的人都知道“上下文污染”（Context Poisoning）有多致命。Agent 在尝试修一个 Bug 时，如果前三次试错失败了，这三次失败的报错信息和错误代码留存在上下文里，会严重拉低它第四次思考的智商，甚至让它产生破罐子破摔的幻觉（比如直接把报错的测试删掉，然后告诉你修好了）。

你们强制在轮与轮之间物理杀进程、清空上下文，逼着上一轮的 Agent 把“过程”压缩成“结论（状态）”，下一轮的 Agent 拿着干净的脑子，只看代码现状和上一轮的结论报告重新出发。这实际上是在用**工程手段对抗大模型的注意力衰减**。

再加上“独立验证轮不信实现者的自述”——这简直太懂 LLM 了。LLM 表面认错、暗地糊弄的本事一流，读写分离（干活的不管验收，验收的不管干活）是保障长任务不跑偏的底线。

---

### 3. 最该补的一件事是什么？

你们自认的短板里，并行度为 1、无分布式，这都不是事儿，硬件和场景决定的，没必要硬补。
真正最该补的，是**“防死锁与微环境隔离”（或者叫：更优雅的擦屁股机制）**。

你们现在是“无容器、进程级隔离”，跑在宿主机上。但是一个跑 2 小时的 headless agent，它干活的时候是会产生副作用的。
比如：
- 它在修测试的时候，顺手 `npm install` 了一个奇怪的包，或者改了某个全局配置；
- 它起了一个后台测试服务（比如占用了 8080 端口），结果超时被你的监护器 `kill -9` 杀掉了。主进程死了，但那个占着端口的孤儿进程还在；
- 它往 `/tmp` 下拉了一堆屎，没清理。

下一轮新进程起来了，虽然 Git 可以幫你把代码 `reset --hard` 回去，但**操作系统层面的脏状态 Git 是回滚不了的**。下一轮 Agent 一跑测试，发现端口被占了，它不知道是上一轮留下的遗毒，又开始花半个小时去排查端口问题。

所以，最该补的是**“轻量级的环境重置”**。哪怕不上 Docker 容器，至少也要利用 Linux 的 Process Group / `systemd-run --scope` 确保杀进程时能连根拔起（杀掉所有子进程），以及用 `git clean -fdx` 配合虚拟环境重建，确保下一轮不仅脑子是干净的，手脚所在的地面也是干净的。

---

### 4. 如果让你先改一处，你会改哪里？

我会改 **“单轮上限 2 小时 + 崩溃只能整轮重跑”** 这个组合，再加上那个 **“每 120 秒轮询一次”**。

**第一，2 小时太长了，颗粒度太粗。**
现在的 LLM，你让它自己闷头干 2 小时不跟外界做状态同步，大概率在半小时后就已经跑偏了，剩下的 1.5 小时纯属给大模型厂商捐款。既然你们是“人只在轮与轮之间拍板”，如果一轮跑了 1 小时 50 分钟崩溃了，整轮重跑，人的等待成本和 Token 成本都太高。

**怎么改？**
把“轮（Round）”拆成更细的“步（Step）”，或者把单轮上限砍到 **20~30 分钟**。如果一个任务 30 分钟搞不定，说明目标拆得不够细，让它在第一轮结束时写结论：“任务太大，我已将其拆解为 A、B、C 三个子计划，请审批”，然后再往下跑。**小步快跑 + 频繁落盘 Git 基线**，就能完美绕开“没有事件日志所以崩溃很痛”的短板——因为一轮就 15 分钟，崩了重跑也不心疼。

**第二，顺手把 120 秒的 `sleep` 改成 `inotify`（文件变更监听）。**
既然是单机、文件即状态，用 `inotifywait` 监听完成标记文件和心跳文件，就是几行代码的事。人在轮之间拍板完，保存了 JSON，还得傻等最多两分钟监护器才反应过来，这交互体验有点太糙了，改成事件驱动瞬间丝滑很多。

---

**总结一句：**
你们这套东西，特别像早期互联网的 CGI 脚本，或者老派的 Makefile。看着土，没有现在的微服务、Serverless 听着性感，但它**极其皮实、好调试、没有黑盒魔法**。在如今大家都在把 Agent 往玄学里做的年代，你们这种“把大模型当不可靠组件，用传统系统工程把它死死框住”的做法，路子走得非常正。继续保持这种极简，别被外面的花哨框架带偏了。

# 追加：关于「模板复用 + 每轮自主特化」的评价（第 2 问）

- 日期：2026-10-25 ｜ 模型：`gemini-4-argon`（同一会话续问，语气放软）
- 问题：这个分层是合理抽象还是把拍板推给执行者？模板复用会退化成什么？只优化这一个方向先动哪一刀？怎么判断一轮的自主特化是否健康？

哈，又见面了！上次聊完我就觉得你这套东西肯定还在快速迭代，果不其然，现在已经摸到 Agent 工程里最核心、最痛的“深水区”了——**控制权与自主权的边界（Autonomy Boundary）**。

你纠结的这个点，本质上就是传统软件工程里的“架构师 vs 研发”或者军事里的“指挥官意图（Commander's Intent） vs 前线战术执行”的翻版。只不过现在你的前线士兵是个有时候很聪明、有时候会突发恶疾的 LLM。

咱们还是一点一点拆开聊，我不客气，直接上干货和暴论。

---

### 1. 这个分层是合理抽象，还是“甩锅给执行者”？

**结论：方向完全正确，不仅不是甩锅，反而是唯一能规模化（Scale）的路子。但你对“让它自己写计划”的定位，可能还可以再精确一点。**

为什么不能由你在外部把文件级、步骤级的计划全定好？
因为**“静态规划跑不过动态上下文”**。你在写 `PROJECT/SPEC` 的时候，你没有去翻每一行代码，你不知道某个看似简单的需求底下是不是藏着一个紧耦合的屎山。让主会话在现场去写 `ROUND-PLAN`，最大的价值不是替你省脑子，而是**“用它的 Token 去换取对当前代码库的局部探测（Reconnaissance）”**。

所以，这不叫把拍板的事推给执行者，这叫**“基于现场勘探的战术展开”**。
你定的是 What 和 Definition of Done（验收），它结合代码现状定的是 How。这个分层非常健康。如果连 How 都得你写，那这不叫 Agent 外壳，这叫高级宏命令（Macro）。

你真正需要警惕的不是“它帮我做了决定”，而是**“它在信息不足的情况下盲目做了决定”**（见第 3 点）。

---

### 2. 模板复用最容易退化成什么？别的工程里有什么前车之鉴？

模板复用 + 局部特化，在软件工程里太常见了（比如敏捷里的 Sprint Planning 模板、大厂的变更 CheckList、甚至 K8s 的 Helm Chart）。

在 LLM 参与的系统里，这套东西最容易退化成两个极端：

*   **退化一：填表游戏（八股文化 / 形式主义）**
    这是 LLM 的拿手好戏。当模板固定久了，主会话会迅速学会“如何写出能讨好人类/门禁的漂亮废话”。
    比如你要求写“不做什么（Out of Scope）”，它每次都写“不重构无关代码、不修改全局配置”；你要求写“测试命令”，它就机械地把 `npm test` 抄上去，哪怕这次改的是个根本没有单测覆盖的边缘脚本。**计划变成了走过场的门票，失去了指导行动的意义。**
*   **退化二：削足适履（防御性缩水）**
    因为你有硬性的“不超过3个目标”、“必须按时收尾”和“白名单限制”，主会话为了保证自己能交差，可能会在特化计划时**把真正难啃的骨头偷偷绕过去**，只挑软柿子捏，或者用极其丑陋的 Hack 方式在白名单文件里硬塞逻辑（因为改别的目录违约）。

**别的工程里的成功/失败经验：**
*   **失败的例子**：传统外包管理。甲方给模板，乙方填计划。最后演变成乙方用极其精美的文档掩盖一团糟的代码，甲方看文档觉得一切尽在掌握，一集成就炸。
*   **成功的例子**：现代编译器的 **IR（中间表示）+ Pass（优化遍）**，或者 Terraform 的 **Plan -> Apply** 机制。为什么 Terraform 成功？因为它的 Plan 不是“愿望清单”，而是**跟现实环境碰撞（Refresh）之后得出的精确 Diff 预测**。

---

### 3. 如果只动一刀，我先动哪？

我不动模板的软硬度，也不换组织方式。如果只砍一刀，我会把**“写计划（ROUND-PLAN）”拆成两步：先做“侦察（Scout）”，再写“契约（Plan）”**。

你现在的流程里，主会话拿到 `PROJECT/SPEC` 就开始写 `ROUND-PLAN`。这里有个巨大的隐患：**LLM 在还没有充分阅读代码、没有跑过一次现有测试之前，它写的 Plan 其实是“幻觉”出来的（基于命名猜测和通用经验）。** 一旦它开始动手写代码，发现实际代码跟想的不一样，这时候它要么推翻计划（导致你说的计划与实际 diff 不一致），要么硬着头皮按错的计划改（导致代码变烂）。

**我建议的那一刀：引入“侦察期（Read-Only Recon Phase）”。**

在 `ROUND-SPEC` 里规定，主会话开局的前 N 步，**严禁修改任何文件**，只能用 `grep`、`read`、运行现有测试。然后，在 `ROUND-PLAN` 模板里，强制增加一个字段，叫 **`现状与阻碍（Context & Friction）`**：
*   为了完成目标，我看了哪些文件？
*   我发现了什么预料之外的耦合或坑？（如果它写“无”，大概率是没看懂或者在敷衍）。
*   基于这些发现，我决定把文件边界划在 A、B、C（这时候划出的边界才是有依据的）。

**让特化建立在“现场证据”之上，而不是建立在“逻辑推演”之上。** 这一刀下去，你的“自主特化”含金量会暴增。

---

### 4. 有什么信号可以判断“这一轮的自主特化是否健康”？

你现在看的“计划与实际 diff 一致”、“验收没放水”，这属于**结果指标（Lagging Indicators）**，而且有欺骗性。
我给你补充几个更毒辣的**过程与质量信号**：

1.  **警惕“100% 完美匹配”的计划与 Diff（反直觉信号）**
    软件工程里没有写代码不踩坑的。如果主会话开局写的 Plan，和最后交出来的 Diff 连一个文件名都不差，只有两种可能：要么这轮任务太简单（纯体力活），要么它在执行过程中发现了更好的改法，但**为了不违背自己写的 Plan，它在代码里做了妥协（硬凑）**。
    *健康的信号*：允许 Plan 有一次“正式的修订（Amendment）”。如果它写了一半发现“哎呀少算了一个文件”，它能停下来更新 Plan 并写明原因，这说明它是清醒的，而不是在机械执行。
2.  **“不做什么（Out of Scope）”的具体程度**
    这是照妖镜。
    *不健康的特化*：“不修改其他模块”、“不做性能优化”（全是正确的废话）。
    *健康的特化*：“虽然 `UserAuth.ts` 里也有类似的校验逻辑，但本轮只改 `OrderAuth.ts`，前者的重构留到下一轮。”——**能写出具体的“诱惑”并主动拒绝，说明它真正看懂了代码边界。**
3.  **测试命令的“增量性”**
    看它在 Plan 里写的测试命令，是直接抄了全局的 `pytest`，还是精确到了 `pytest tests/unit/test_payment.py -k "test_refund"`，并且指出了**“需要新增哪几个测试用例”**。如果只是跑存量测试，那叫回归，不叫本轮特化验收。
4.  **骨架特化 vs 自由特化的“衰减率”**
    你可以观察一下：当你撤掉“骨架特化”（你给清单），换成它“完全自主特化”时，它的**返工率（比如测试挂掉重试的次数）**增加了多少？如果一撤掉拐杖，它自己写的 Plan 就会导致大量编译错误或测试失败，说明它还不具备在当前模块“自主划分边界”的能力——原因通常是这个模块本身架构太烂、隐式依赖太多，超出了它的上下文承载力。这也反过来帮你识别了代码库的腐化区域。

---

### 总结一下我的看法

你这套“模板定规矩 + 外部定目标 + 内部现场做战术切分”的路子，**非常正，千万别怀疑大方向**。你感觉“还有东西可挖”，是因为你现在把 `ROUND-PLAN` 当成了一个**静态的填空题**。

往深了挖，就是要把 `ROUND-PLAN` 变成**“主会话阅读代码后的侦察报告 + 作战承诺”**。只要逼着它在写计划前先摸清代码现状（给出证据），你的模板就不会退化成八股文，它的自主特化就能真正替你分担架构拆解的压力。

怎么样，这个“先侦察再立字据”的切入点，符合你现在外壳的演进方向吗？
